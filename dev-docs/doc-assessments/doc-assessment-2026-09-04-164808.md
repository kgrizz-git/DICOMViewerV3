## Purpose and boundary

This record establishes an auditable baseline for the documentation-freshness
workflow. It inventories the documentation surfaces, records the checks that
already exist, and identifies the first audit slices for Phase 1. It does not
claim that user documentation, developer documentation, or docstrings are
complete or semantically accurate.

The assessment was gathered independently by three read-only review lanes and
then checked against the repository by the coordinator. One reviewer correctly
identified unclear proposed PR-template terminology and missing automation;
its assertion that `RELEASING.md` lacks an assessment cadence was rejected:
the current release guide already requires an assessment after a minor/major
release or a large UI/Help change. The remaining gap is enforcement and
traceability, not the absence of a stated cadence.

This table is the initial ownership map. Phase 1 must turn each candidate
coverage gap into one of: **document**, **intentionally omit**, **duplicate**,
or **obsolete**, with a linked issue or bounded follow-up for unresolved work.

## Existing maintenance controls and gaps

### Link integrity

The link checker runs in CI and correctly prevents user documentation from
linking to planning/backlog material. It does not validate anchor-only links,
external URLs, all developer Markdown, in-app HTML placeholders, or the
programmatically-built About content. The harness supplements this with a
small selected set of repository documents and required user-guide topics.

### Feature-to-document discovery

`check_doc_feature_coverage.py` gives useful candidate gaps, but it is
report-only unless a threshold is supplied and does not establish that the
documented behavior is current. Its literal QAction extraction excludes some
actions introduced through other Qt APIs, so the result is a lower-bound
inventory rather than a final coverage measure. No durable triage ledger yet
exists for the 34 candidates.

### Assessment cadence and docstrings

`dev-docs/RELEASING.md` states the assessment cadence, but CI and the release
workflow do not assert that an assessment record exists. The current
assessment template also contains stale path references and requires a focused
review before its next reuse. Docstring tooling measures presence only; no
automated check can determine behavioral accuracy or completeness.

## Phase 1 priorities

1. Audit the user-guide hub, Quick Start, configuration, and core viewing/
   navigation topics against the current application and in-app Help routes.
2. Triage every current feature-coverage candidate into the four ownership-map
   outcomes, recording deferred work explicitly.
3. Define the high-risk docstring audit list and review those docstrings
   against code for defaults, side effects, error behavior, and terminology.
4. Reconcile the Help HTML, `doc_urls.py`, topic Markdown, and About content
   where they describe the same user workflow.
5. In a follow-up governance change, make release-assessment traceability and
   PR-template terms unambiguous; evaluate narrow automation before adding
   more mandatory checks.
